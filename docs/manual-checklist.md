# 手動確認のチェックリスト

自動テストで確かめられない、実機とブラウザの挙動を確かめる。リリースの前に、このファイルをコピーして（たとえばリリースの PR やリリース ノートの下書きに）チェックを入れていく。

## いつ通すか

- 次のどれかを変えたリリースでは、**OrbStack（私用: macOS + OrbStack）と WSL2（公用: Windows + WSL2）の両方で**すべての項目を通す。
  - ログイン（ログイン URL とトークン、セッション Cookie、ログアウト、Origin の検証）
  - Host の検証
  - unit の生成（`install-service` / `uninstall-service`）
  - フロントエンドの JS（htmx の設定、テンプレートの `hx-*` 属性、`internal/server/static/` の JS）
- それ以外の変更だけのリリースでは、通さなくてよい（通すならどちらか一方の環境で十分）。

## 準備

- ゲストのストアに、複数行のエントリ（1 行目がパスワード、2 行目以降に `user: …` などの `key: value`）を 1 つ以上用意しておく。
- 確かめるリリースを入れる: `mise use -g github:backpaper0/passui@<version>`（更新なら `mise upgrade passui`）。
- `passui version` が、そのバージョンを出す。

### install-service からの起動

- [ ] `passui install-service` が警告（あれば）を出したあと、ログイン URL を表示して終了コード 0 で終わる。
- [ ] `~/.config/systemd/user/passui.service` の `ExecStart` が mise の shim（`~/.local/share/mise/shims/passui serve`）になっている。
- [ ] `systemctl --user status passui` が active (running)。`journalctl --user -u passui` に起動のログが出ている。
- [ ] もう一度 `passui install-service` を実行しても同じ結果になる（unit が変わらず、新しいログイン URL が出る）。
- [ ] `systemctl --user stop passui` で止まり、`passui login` が「起動していない」と出す。`systemctl --user start passui` で戻る。

### ログイン URL

- [ ] `passui login` がログイン URL（`http://passui.localhost:<port>/login?token=…`）を出す。
- [ ] ホストのブラウザで開くと、アドレスバーからトークンが消えて `/` に移り、2 ペインの画面が出る。
- [ ] ログアウトすると、案内ページ（`passui login` を案内する）が出る。戻るボタンで前の内容が見えない。
- [ ] 案内ページにもトップ ページと同じ CSS が当たり、ブラウザのタブに passui の favicon が出る。
- [ ] passui を再起動すると、前のセッションでは案内ページになり、新しい `passui login` の URL でログインし直せる。

### passui.localhost への到達

- [ ] ホストのブラウザから `http://passui.localhost:<port>/` に届く。
- [ ] `http://localhost:<port>/` や `http://127.0.0.1:<port>/` ではログインできず、`passui.localhost` を使うよう案内される。
- [ ] LAN 上の別の機械からは届かない（ホストの LAN の IP とポートで開けない）。

### ロックと解錠の表示

- [ ] 解錠中・ロック中がヘッダーのバッジで分かる。
- [ ] ロック ボタンに「ターミナルの pass もロックされます」とあり、押すとロック中になり、右ペインの詳細が消える。ログインは続いている。
- [ ] 編集フォームに入力している途中でロック、またはログアウトすると、確認なしで入力が消える。どちらの後も、戻るボタンで前の詳細が見えない。
- [ ] ロック中にエントリを開くと、エントリ名入りの `pass show <エントリ> >/dev/null`、コピー ボタン、再試行ボタンが出る。
- [ ] ゲストのターミナルでそのコマンドを実行して解錠し、ブラウザに戻ると、再試行を押さなくても詳細が出る。

### 伏せ字と表示の切り替え

- [ ] 詳細を開くと、パスワード（1 行目）は伏せ字で、2 行目以降の `key: value` はそのまま見える。
- [ ] 目のアイコンのボタン（「表示」）でパスワードが見え、アイコンが斜線入りの目に、ツールチップが「隠す」に変わる。もう一度押すと伏せ字に戻り、「表示」に戻る。
- [ ] 別のエントリに切り替えると伏せ字に戻り、ボタンも「表示」に戻る。

### 45 秒後のクリア

- [ ] パスワードと各値のコピー ボタンでクリップボードに入り、残り秒数が表示される。
- [ ] 45 秒後にクリップボードが空になる（どこかに貼り付けて確かめる）。
- [ ] 45 秒になる前にほかのウィンドウへフォーカスを移すと、その時点ではクリアできず、passui のタブにフォーカスを戻したときに 1 回だけクリアされる。

### タブが非表示になったら伏せ字に戻す

- [ ] 「表示」でパスワードを見せたまま、別のタブに切り替えるかウィンドウを最小化して戻ると、伏せ字に戻っている。

### bfcache から戻ったときの読み直し

- [ ] 詳細を開いたまま別のサイトに移り、戻るボタンで戻ると、ページが読み直される（ロックやログアウトの後なら、平文が出ずに現在の状態が出る）。

### htmx による部分更新

- [ ] エントリを選ぶと、ページ全体ではなく右ペインだけが変わる（アドレスバーやツリーの開閉状態が保たれる）。
- [ ] 選んだエントリがツリーでハイライトされる。編集・削除の確認・ロック中の案内でもハイライトは残り、検索結果でもハイライトされる。削除した後と新規作成のフォームではハイライトが消える。
- [ ] 検索欄に打つと、一致したパスが平らに並び、一致した部分が強調される。
- [ ] 新規作成・編集（移動を含む）・削除・再生成の後、ツリーが読み直される。
- [ ] ゲストのターミナルで `pass insert` や `pass rm` をしてからタブに戻ると、ツリーが読み直される。
- [ ] 編集を開いたままターミナルで `pass insert -f` をしてから保存すると、入力が残ったまま競合の案内が出る。「それでも上書きする」で保存でき（押したボタンの値が送られる）、「最新を読み直す」で入力が捨てられて最新の本文が出る。
- [ ] 別のタブでログアウトしてから元のタブで操作すると、画面の一部だけが壊れずに案内ページに移る。
- [ ] 失敗したとき（たとえば既にあるエントリ名で作成）、右ペインに分類したメッセージが出る。

### エクスポート

- [ ] 私用（macOS の Chrome）でエクスポート ボタンを押すと、画面が変わらずに `passui-export-YYYYMMDD-HHMMSS.tar.gz`（ゲストのローカル時刻）がダウンロードされる。ロック中に押しても同じ。
- [ ] 公用（Windows の Edge）でエクスポート ボタンを押すと、同じくダウンロードされる。
- [ ] ダウンロードしたファイルを展開すると、同じ名前のディレクトリの下に `store/`、`gnupg/`、`README.txt` がある。
- [ ] ゲストの `.gpg-id` に存在しない鍵 ID を足してからエクスポート ボタンを押すと、ダウンロードされずに結果ページが出て、その鍵 ID が並ぶ（確かめたら `.gpg-id` を戻す）。
- [ ] ストアの鍵の `.key`（`$(gpgconf --list-dirs homedir)/private-keys-v1.d/<keygrip>.key`）を `chmod 000` にしてからエクスポート ボタンを押すと、ダウンロードされずにエラー ID 付きの結果ページが出て、そのエラー ID が journald のログにある（確かめたら `chmod 600` で戻す）。
- [ ] エクスポートファイルを空の新しいゲスト（または新しい `GNUPGHOME` と `PASSWORD_STORE_DIR`）に写し、`README.txt` の手作業で戻す手順を文字どおりになぞると、元のパスフレーズで `pass show` が通り、`gpg --batch -e -r <指紋>` が警告なしに通り、`git log -1` がエクスポートした時点のコミットを出す。
- [ ] `README.txt` で、passui でインポートする方法が手作業で戻す手順より先に書かれている。

### インポート

- [ ] ストアがあるゲストでは、左ペインにインポートのフォームが出ない。
- [ ] 空の新しいゲスト（または、unit の `PASSWORD_STORE_DIR` と `GNUPGHOME` を新しい空のディレクトリにして `install-service` し直したゲスト）で passui を起動してログインすると、左ペインの「エントリがありません」の下にインポートのフォームが出る。
- [ ] 私用（macOS の Chrome）で、エクスポートでダウンロードしたファイルを選んでインポートすると、「インポートしました。ターミナルで解錠し、エントリを開いて確かめてください」と出る。トップに戻るとツリーにエントリが並ぶ。
- [ ] 公用（Windows の Edge）でも、同じくインポートできる。
- [ ] インポートした後、ゲストのターミナルで元のパスフレーズで `pass show <エントリ>` が通り、`echo test | gpg --batch -e -r <指紋> >/dev/null` が警告なしに通り、`git log -1` がエクスポートした時点のコミットを出す。passui の画面でもエントリを開ける。
- [ ] `$(gpgconf --list-dirs homedir)/private-keys-v1.d` が `0700`、置かれた `<keygrip>.key` が `0600`。展開に使った一時ディレクトリ（`/tmp/passui-import-*`）が残っていない。
- [ ] インポートのフォームを開いたまま、ゲストのターミナルでストアに何か置いてから送ると、「ストアが空ではないので、インポートしませんでした」と出て、ストアは変わらない。
- [ ] エクスポートファイルでないファイル（適当なテキストファイルなど）を送ると、「エクスポートファイルとして受け付けられません」と出て、ゲストには何も書かれない。
- [ ] ストアだけを消し、秘密鍵（同じ keygrip の `.key`）を残したゲストで、そのストアのエクスポートファイルを送ると、「同じ秘密鍵がゲストにすでにあるので、インポートしませんでした」と出て、すでにある鍵の keygrip が並ぶ（`gpg -K --with-keygrip` の Keygrip と同じ）。ストアは作られず、`private-keys-v1.d` も変わらない。passui のログには keygrip が出ない。

### 削除

- [ ] `passui uninstall-service` で止まり、unit が消える。linger、`gpg-agent.socket`、`~/.config/passui/env` はそのまま。
- [ ] もう一度実行すると「登録されていません」で何もせずに終わる。
